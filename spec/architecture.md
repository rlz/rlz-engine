# Architecture

This note describes the current structure of the `rlz-engine` package. Its package manifest and TypeScript sources live at the repository root; the former `sample-project` demo has been removed.

## Package layout

- `src/back` contains Fastify server setup, RPC registration, authentication, and MongoDB storage helpers.
- `src/client` contains browser-side RPC transport, generated API usage, synchronization logic, and client state.
- `src/shared` contains schemas and types used across the client/server boundary, plus shared utilities.

The package exports compiled `back`, `client`, and `shared` modules from `dist` according to the root `package.json`.

The package requires Node.js 22.13 or newer for the built-in `node:sqlite` API used by production audit storage.

## RPC contract and code generation

User RPC declarations use `rpc()` and administrative declarations use `admRpc()` from `src/back/rpc/rpc.ts`. Each endpoint carries a name, integer version, Zod body and response schemas, and an action. These declarations contain no Fastify registration code; the HTTP server maps them to routes under `/rpc/<group>_<endpoint>_v<version>` and `/.adm/rpc/<group>_<endpoint>_v<version>`. User routes are anonymous or require cookie authentication with a CSRF verifier. Administrative routes require `Authorization: Bearer <admin-secret>`, verified against `./auth/admin-secret` by the HTTP server. RPC dependencies are captured in handler closures; engine composition and client generation work from declarations directly.

`src/back/rpc/gen.ts` turns registered endpoint schemas into TypeScript body/response types and client objects. `generateClient()` handles user RPC and `generateAdmClient()` handles administrative RPC. The administrative generator adds the built-in auth declaration when it is absent and recognizes the exact built-in declaration when passed the already-composed `RlzEngine.admRpc` list. User client methods take only their request body and use same-origin cookies. The generated administrative client requires an `AdmAuthParam` with the admin secret and calls `admRpcCall()`, which sends `Authorization: Bearer <admin-secret>` to `/.adm/rpc/...`. Separate generators and transport functions keep administrative credentials out of user RPC. Keep endpoint versions, shared schemas, and generated client expectations aligned when changing a contract.

## Authentication and client transport

The browser RPC helper serializes requests as JSON, compresses bodies larger than 16 KiB with gzip, and sends user RPC with same-origin cookies plus the CSRF token held in memory. `admRpcCall()` uses the separate administrative route prefix and sends the admin secret as a Bearer token. Both map common HTTP statuses to dedicated error classes. The backend RPC registration provides handlers a request context with headers, parsed cookies, protocol, and cookie-setting methods. Cookie-auth endpoints authenticate from that context and must verify CSRF before invoking the action.

`runServer` registers the external `@fastify/cookie` plugin directly on the development HTTP server and production HTTPS server before application routes. `src/back/auth/cookies.ts` exports session-cookie helpers that always set `HttpOnly`, `Secure`, and `SameSite=Lax`, use `Path=/`, and omit `Domain`; callers can configure only the cookie lifetime. `src/back/auth/csrf.ts` exports utilities that create 256-bit synchronizer tokens, compare them in constant time, and require the request Origin to match its own origin. CORS is enabled only in development and does not allow credentials; production apps serve the frontend and RPC from the same HTTPS origin. The built-in auth feature provides opaque server-side sessions, session rotation at signin, idle and absolute expiry, logout revocation, and CSRF-protected cookie authentication.

The auth endpoint implementations and persistence live under `src/back/auth`. `AUTH_MODULE.makeRpc(storage, options?)` registers signup at `/rpc/auth_signup_v1` and signin, session restoration, and logout at `/rpc/auth_*_v1`; `options.sessionIdleTimeoutMs` configures the idle timeout (30 minutes by default, capped at the fixed seven-day absolute timeout). Their schemas live with the auth feature, and applications generate browser clients from this builder. Signup accepts passwords of 12–1024 characters and returns an empty success response whether the name was created or already existed; the browser client then signs in. This avoids exposing name occupancy through the signup response while preserving the signin contract. Signin sets an HttpOnly cookie and returns a synchronizer token. Signup and signin are rate limited per peer IP (5 signup attempts per hour and 10 signin attempts per 15 minutes), with at most four concurrent auth operations per process; these in-memory limits do not coordinate across multiple server processes. Signin passwords are capped at 1024 characters for bounded hashing work; existing shorter passwords remain accepted. The session endpoint returns the profile and token for a valid cookie. Session IDs are 256-bit random values; MongoDB stores their SHA-256 hashes, CSRF token, and timestamps. Logout deletes the current session. Existing user documents without `passwordHashVersion` are treated as legacy scrypt records. A successful signin verifies the old hash with its original parameters and atomically upgrades it to version 1; newly created accounts use version 1. Browser profile state lives in `src/client/state/auth.ts` and is persisted by Zustand, while the CSRF token remains in memory and is restored through the session endpoint.

## Feature modules

Each cohesive feature lives in its own directory and exposes a `module.ts` entry point with an uppercase `<FEATURE>_MODULE` object (for example, `LOGGER_MODULE`). The object provides only the integration factories the feature needs, such as `makeCli()`, `makeDevCli()`, `makeRpc()`, `makeAdmRpc()`, or `makeAdm()`; absent facets are omitted. Applications invoke selected factories and pass production facets to `rlzEngine()` in `src/back/engine.ts`. It resolves promised facets and arrays, validates duplicate names, and registers user/admin RPCs; deployment settings and application-owned RPC actions remain in the application modules. Development commands use a separate `DevCliEngine` in a development-only entry point and are not accepted by `rlzEngine()`.

## Optional library modules

`rlzEngine()` accepts server `cli`, `rpc`, and `admRpc` facets and exposes their resolved lists alongside `run()`. The standard `auth.verify` endpoint is included in `admRpc`. RPC handler dependencies are captured by declarations, usually through asynchronous facet factories. CLI commands receive the active engine when invoked. `HTTP_MODULE.makeCli()` passes the resolved `rpc` and `admRpc` lists in the same options object as server settings to `runServer()`, which owns all Fastify route registration. Administration UI modules are client-side inputs to `AdminApp` and are not collected by the server engine. Development-only commands are wired through `rlzDevEngine()` in a separate entry point, keeping client generation out of production command registration. HTTP lifecycle hooks remain on `HTTP_MODULE.makeCli()`. User RPC uses `/rpc/<group>_<endpoint>_v<version>` and administrative RPC uses `/.adm/rpc/...` with the administrative Bearer secret. The administration UI and shared auth state are provided by `AdminApp` and `client/adm/auth.js`. `LOGGER_MODULE` and `CERTIFICATE_MODULE` provide optional administration sections and corresponding RPC endpoints. Applications own deployment settings and RPC action dependencies.

`CliEngine` and `DevCliEngine` build separate command trees. `rlzEngine()` runs production CLI facets; `rlzDevEngine(engine, commands)` adds development commands to a wrapper around the initialized engine. Development commands receive that same resolved engine at invocation, so `RPC_MODULE.makeDevCli()` reads `rpc` and `admRpc` from the command context and only needs output paths. Every command has a description, and nested help follows the command tree. `AUTH_MODULE.makeRpc(storage)` contributes authentication RPC, `AUTH_MODULE.makeCli()` contributes `adm reset-secret`, `CERTIFICATE_MODULE.makeCli()` contributes `certificates register-acme`, and `HTTP_MODULE.makeCli()` contributes `http start`. The HTTP module retains its `before` and `after` lifecycle hooks, with shutdown on an after-hook failure.

User RPC no longer supports per-endpoint Bearer credential callbacks. Authenticated user endpoints use cookie sessions and CSRF verification; public endpoints are explicitly anonymous. Applications that used the removed callback must migrate to cookie authentication. Administrative RPC retains its separate Bearer secret contract. The production application RPC server is the TLS server; the separate unsecure server handles ACME HTTP-01 and redirects. The legacy `/api/...` protocol and its transport have been removed.

The `adm reset-secret` command is provided by `AUTH_MODULE.makeCli()` and runs through an application's `CliEngine`; the library does not expose a separate executable for it. It writes a salted scrypt record to `./auth/admin-secret` relative to the current working directory, then prints the newly generated secret once. The file is atomically replaced with mode `0600`; each invocation resets the previous secret. `verifyAdminSecret` caches the parsed record in memory by absolute path, so the file is read once per process and path. Missing or malformed records deny access. Because secret generation runs in a separate CLI process, a running HTTP server keeps its cached record until it restarts. Administrative RPC routes use the verifier. The React administration UI is mounted by applications at `/.adm`. It asks for the admin secret and uses it as a Bearer credential for protected administrative RPC calls; the UI keeps the credential only in memory and requires re-entry after reload. Administration modules contribute a default view and may declare additional child navigation views with their own components. `AdminApp` derives navigation from registered modules and presents it in a responsive drawer. Built-in modules include audit-log browsing and certificate status (issue time, expiration time, time until planned renewal, and whether renewal is overdue).

## Logging and audit trail

Logger implementations live in `src/back/logger/`, with imports targeting their implementation modules directly. `src/back/logger/module.ts` exports `LOGGER_MODULE`; `makeAdmRpc()` creates the protected audit-log query builder and `makeCli()` creates the audit-log reader command module. Application modules call `getAuditLogger<EventUnion>(module)` to get a module-scoped `AuditLogger` with level methods and strongly typed event objects. Each event has a `type` discriminant; its other fields are stored in `data`. Applications can compose domain-specific logger wrappers with methods such as `userRegistered`, sharing the typed `AuditLogger` beneath them. `initAuditLogger` selects one of three modes: console, SQLite, or SQLite plus console. Logger instances obtained before initialization remain no-op until a sink is selected, and return to no-op after the sink is closed. `runServer` defaults to SQLite only in production when debug is disabled, and colored console only otherwise. In console mode, `RunServerParams.auditSqlite` or the HTTP CLI `--audit-sqlite` flag enables SQLite alongside the console. `getSystemLogger(name)` creates a Fastify-compatible `SystemLogger`, which forwards records to module `SYSTEM`, uses the Fastify message as the event type, and retains its logger name in structured data; it prints readable single-line records to stdout in production.

Audit records contain time, level, module, event `type`, structured `data`, and optional error details including stack trace. Structured fields are serialized for storage without secret-field redaction; callers are responsible for not logging secrets. Production `runServer` writes to `logs.sqlite` in the application working directory. Retention defaults to 30 days and the global record limit defaults to 100,000; both can be overridden in `RunServerParams`. `SqliteAuditStorage` creates indexes by time, module, and level, prunes expired/excess records on startup and hourly, and closes with the server. `getAuditLogReader()` returns an `AuditLogReader` that can filter by inclusive time bounds, module, and level, and paginate newest-first with a stable time-and-ID order and a page limit of 1000; it returns an empty page when SQLite is not the active sink. `LOGGER_MODULE.makeAdmRpc()` creates an administrative endpoint exposing this query at `/.adm/rpc/audit_logs_v1`, with optional filters and defaults of 100 records and offset 0. `LOGGER_MODULE.makeCli()` adds `logger logs`, which reads an existing SQLite file in read-only mode and accepts `--from`, `--to`, `--module`, `--level`, `--limit`, and `--offset`; it prints matching records with the same colored, multi-line formatter used by the live console sink. Administrative route authentication uses the admin Bearer secret. Its `DatabaseSync` reads and writes are synchronous; storage errors are reported to stderr without interrupting application or SystemLogger output.

## Data synchronization

The shared synchronization schemas define the wire format for listing comparison metadata, fetching objects by ID, and pushing objects. Server storage helpers list an owner's object IDs and `lastModified` values, optionally filtered by a sync timestamp. The client compares those timestamps with local items: newer local items are pushed, while newer or previously unknown remote items are fetched and passed to the local update callback.

The sync helpers coordinate metadata and transfer; application-specific merging and durable client storage are supplied by their callers.

## Storage and server lifecycle

`MongoStorage` wraps MongoDB access and reconciles configured collection indexes by removing obsolete named indexes and creating missing ones. Storage model helpers use string UUIDs and carry owner and synchronization metadata.

`runServer` configures Fastify. Development serves on the unsecure port with CORS and static routes. Production starts the HTTP server for ACME HTTP-01 and redirects, obtains the certificate, then starts an HTTP/2-capable TLS server with HTTP/1 fallback and periodic certificate renewal. Both servers are closed by the returned shutdown function.
